# 02 — World-to-Agent Compilation Method

## Purpose

Translate real-world structures without flattening them into superficial analogy.

## Stage 0 — Raw human observation

Capture the phenomenon before explaining it.

Required:
- what exists;
- what actors/components exist;
- local interactions;
- constraints;
- resource flows;
- failure conditions;
- time scale;
- environmental pressures.

Do not mention Agents yet.

## Stage 1 — Structural invariant

Ask:

> If the biological/social names are removed, what relation pattern remains?

Example:

Instead of:
“fungi are a network.”

Prefer:
“a decentralized substrate expands locally, retracts from low-value regions, routes resources along gradients, survives partial damage through redundant paths, and stores continuity in the network rather than a central controller.”

## Stage 2 — Primitive extraction

Compress into reusable machine terms.

Example:
- local_growth
- selective_decay
- resource_gradient
- redundant_routing
- distributed_memory
- structural_regeneration

A primitive should be:
- domain-independent;
- composable;
- behaviorally meaningful;
- testable where possible.

## Stage 3 — Agent provocation

Do NOT immediately prescribe an architecture.

Ask constrained questions such as:

- What Agent architecture becomes thinkable if these primitives are mandatory?
- Which conventional component becomes unnecessary?
- What new failure mode appears?
- What property emerges only from interaction?
- Under what environment would this architecture outperform a conventional baseline?

## Stage 4 — Cross-domain composition

Combine structures from unrelated domains.

Examples:
- fungal routing × immune memory × monastery roles;
- octopus nervous system × city logistics × market pricing;
- coral symbiosis × legal precedent × swarm quorum;
- forest succession × ephemeral workers × software versioning.

The goal is not poetic novelty.  
The goal is new **mechanism combinations**.

## Stage 5 — Architecture species generation

Every generated architecture receives:
- species_id;
- parent_prior_ids;
- primitive set;
- interaction rules;
- emergent property;
- expected advantage;
- expected weakness;
- falsification condition;
- minimal sandbox test;
- nearest conventional baseline.

## Stage 6 — Reality check

For each proposal ask:
- is the source mechanism accurately represented?
- is the abstraction too loose?
- is the Agent mapping merely metaphor?
- does the proposed behavior already exist under another name?
- can the claim be falsified?
- can it be tested cheaply?

## Stage 7 — Archive, do not overbuild

Most generated architectures should be archived, not implemented.

Implementation priority should be reserved for architectures that score highly on:
- architecture distance;
- practical plausibility;
- measurable advantage;
- test cost;
- safety;
- reusability.
